# Sakemem パフォーマンス改善方針 — 調査と対策

> 作成日: 2026-06-27  
> ステータス: 計画中  
> 関連: [Sakemem_Context.md](../Sakemem_Context.md), [sharing-feature.md](./sharing-feature.md)

## 1. 背景と現状の課題

ユーザーより「全体的に動作がもたついた印象を受ける」とのフィードバックがあり、原因の調査を行った。
特に「タイムラインでの検索・フィルタリング」および「各画面へのページ遷移」において遅延が顕著である。

### もたつきの真の原因

現在の Sakemem は Next.js の Server Components (SSR) をベースに構築されているため、画面遷移やフィルタリングのたびに以下の箇所でボトルネックが発生している。

1. **タイムラインでのフィルタリング時の再描画**:
   - `RecordFiltersForm` が `<form method="get">` を使用しており、検索時に URL クエリパラメータを更新してページ全体をサーバー側で再レンダリング (SSR) している。
   - サーバー側での再レンダリングのたびに、`requireUser()` (認証セッションチェック) と `getRecords()` (Supabase からのデータ全件取得) という外部ネットワーク通信が毎回発生する。
2. **ページ遷移時のフリーズ感**:
   - `/records` ➔ `/records/new` や `/records/[id]/edit` などの遷移時にも、遷移先ページの Server Component 内でセッションチェックや DB 取得を待機する。
   - これらが完了するまでブラウザ側での描画が開始されないため、クリックしてから画面が切り上がるまでの「もたつき（無反応時間）」となる。

---

## 2. 改善方針（ハイブリッド構成の採用）

将来の「[共有機能 (Phase A)](./sharing-feature.md)」の実装（SNS への動的 OGP 展開）を阻害せず、かつ SPA のようなサクサクした操作感を提供するために、**ページ単位でレンダリング方式を使い分けるハイブリッド構成**を採用する。

| 領域 | ルート / 機能 | レンダリング方式 | 改善内容 |
| :--- | :--- | :--- | :--- |
| **プライベート領域 (要認証)** | `/records`<br>`/records/new`<br>`/records/[id]/edit` | **SPA風 (Client-side Fetch / UI-first)** | - タイムラインのクライアントサイド・フィルタリング化<br>- `loading.tsx` の導入による即時ローディング遷移 |
| **パブリック領域 (共有用)** | `/@[username]`<br>`/@[username]/[id]` | **SSR (Server-side Rendering)** | 外部クローラーが JavaScript なしで動的 OGP メタデータを読み取れるよう、サーバー側で結合して HTML を生成する。 |

---

## 3. 具体的な実装方針

### 3.1 タイムラインのクライアントサイド・フィルタリング移行

最も頻繁に使用されるタイムラインの絞り込みを、サーバー通信なしで瞬時に完了させる。

- **実装方針**:
  - `RecordsPage` (`src/app/records/page.tsx`) は初期ロード時に `allRecords` を一度だけフェッチし、新しく作成するクライアントコンポーネント（例: `TimelineContainer`）に流し込む。
  - クライアント側で `useState` を使って検索文字列（`query`）、種別（`kind`）、カテゴリ（`category`）を管理。
  - 入力が変更されるたびに、ブラウザ上のメモリ内で `filterRecords` を実行し、タイムラインと統計情報を 0 秒で更新する。ボタンによる Submit を必要としないリアルタイム検索も可能とする。

### 3.2 遷移もたつきの解消: `loading.tsx` の導入

ページ遷移時の「フリーズしている感覚」を解消する。

- **実装方針**:
  - `src/app/records/loading.tsx` や `src/app/records/[id]/edit/loading.tsx` を新規作成する。
  - サーバーがデータをフェッチしている間、クライアント側で即座にスケルトンや進捗バーを描画し、体感上の待ち時間をゼロにする。

## 4. 将来の共有機能との整合性（検証）

[docs/sharing-feature.md](./sharing-feature.md) に計画されている共有ページは、クローラーに動的なメタデータ（OGP）を渡す必要がある。

- **影響**: アプリ全体を一律で SPA 化（`next.config` での完全静的エクスポートや SSR 無効化）してしまうと、クローラーが HTML を読み込んだ際に動的メタデータが空になってしまい、共有機能の価値が失われる。
- **解決策の妥当性**: 今回提案した「プライベート領域のみ SPA 風にし、パブリック共有ページは SSR を維持する」ハイブリッド設計により、この問題は完全にクリアされる。

---

## 5. 段階的改善ロードマップ（改善計画）

影響範囲を抑え、安全かつ確実にパフォーマンスを向上させるため、以下の 4 ステップで実装を進める。

### Step 1: ページ遷移の高速化（ローディングUIの導入）
最も迅速に適用でき、全体の遷移ストレスを大幅に軽減する。

1. **`src/app/records/loading.tsx` [NEW]** の作成
   - タイムラインカードのダミー（スケルトン）を 3〜4 件配置したプレースホルダーUIを作成。
2. **`src/app/records/new/loading.tsx` [NEW]** / **`src/app/records/[id]/edit/loading.tsx` [NEW]** の作成
   - フォーム全体の形状を模したシンプルなローディングスケルトンを配置。
3. **検証**: ページ遷移時に無反応で固まる時間がなくなり、クリックした瞬間にローディング表示へ切り替わることを確認。

### Step 2: タイムラインのクライアントサイド・コンテナの構築
タイムライン画面のレンダリング構造をリファクタリングする。

1. **`src/components/records/timeline-container.tsx` [NEW]** の作成
   - `"use client"` ディレクティブを指定したクライアントコンポーネント。
   - `allRecords` を props で受け取る。
   - `useState` を用いて、`query`, `kind`, `category` の状態（状態の初期値は URL パラメータから同期可能にしておく）を管理する。
2. **`src/app/records/page.tsx` [MODIFY]** の変更
   - `RecordFiltersForm` や `Timeline` を直接呼び出すのをやめ、取得した `allRecords` を `TimelineContainer` に渡してレンダリングを委ねるように変更。

### Step 3: フィルタフォームとタイムライン表示のリアクティブ化
サーバーへの GET リクエスト送信を廃止し、クライアントサイドで動的に表示を切り替える。

1. **`src/components/records/record-filters.tsx` [MODIFY]** の変更
   - `<form method="get">` を廃止し、フォームの `submit` でページの再ロードが発生しないようにする（または `form` 要素のデフォルト動作を抑止）。
   - キーワード入力（`input`）や種別・カテゴリ（`select`）の変更イベント（`onChange`）を検知し、`TimelineContainer` が持つステートを即時更新するように接続する。
2. **パフォーマンス向上とリアルタイム性確保**:
   - テキスト入力時にタイプごとに処理が走るため、負荷が気になる場合は簡単なデバウンス（Debounce）処理（300ms程度）を挟み、入力が落ち着いてから絞り込みを行うようにする。
   - 絞り込み結果に応じて `Timeline` および `RecordStats` の集計データが即座（0ms）に更新されるようにする。

### Step 4: 動作検証とパフォーマンス測定
1. **動作確認**: 検索キーワードの入力、種別・カテゴリの変更で画面全体のリロードが発生しないことを確認。
2. **セッション挙動の確認**: ページ内遷移やデータの追加・編集後のリダイレクト時も、キャッシュが適切に更新され、最新のデータがタイムラインに正しく反映されるか（Server Actions の `revalidatePath` が期待通り働くか）を検証。
